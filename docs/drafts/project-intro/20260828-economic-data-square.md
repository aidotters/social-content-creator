経済のデータを1枚のグラフにしたい、と思ってから実際にグラフができるまでの間に、だいたい30分くらいの単純作業が挟まります。

統計を公表しているサイトを開く。目的の表を探す。Excel か CSV をダウンロードする。開いてみると、ヘッダーが3行あって、単位が「億円」と「百万円」で混ざっていて、系列が横に並んでいる。それを整形して、別の統計と時点を揃えて、ようやくグラフにできる。

1回だけならいいのですが、これを毎回やることになります。しかも次に同じことをするときには、前回どう整形したかを忘れています。

**経済データスクエア**（[econ.aidotters.com](https://econ.aidotters.com)）は、この30分をなくすために作ったサイトです。世界銀行や日本の各省庁が公表している経済統計を1か所に集めて、指標を探して選ぶと、そのままグラフになります。

本記事では、このサイトの設計で考えたことを、うまくいかなかった部分も含めて書きます。

## 何ができるか

現在は13の公的機関のデータが入っています。世界銀行、e-Stat（政府統計の総合窓口）、日本銀行、財務省、内閣府、欧州中央銀行、米国財務省、厚生労働省、経済産業省、国土交通省、総務省統計局、内閣府経済社会総合研究所、日本政府観光局です。

画面は4つあります。

- **世界経済ダッシュボード** — 主要国のマクロ指標を並べて比較する
- **日本経済ダッシュボード** — 日本の公的統計をまとめて見る
- **国別プロファイル** — 1国分の指標を、G20内の順位つきで俯瞰する
- **チャートスタジオ** — 指標を自分で選んで、折れ線・棒・散布図などに描いて画像として書き出す

データは毎朝9:30に各出典から取り直しています。月曜はすべての出典、それ以外の日は金利や為替のように日々動くものと、公表があったときだけ更新される統計を取りに行きます。

## 設計で一番考えたこと: 改定前の数値をどう扱うか

経済統計には、**あとから数値が変わる**という性質があります。

たとえばGDPの速報値は、その後の1次速報・2次速報で改定されます。「2026年4-6月期の実質GDP成長率は年率1.2%」と発表された数字が、3か月後には0.8%になっていることがある。改定自体は正常な運用で、より正確な情報が集まった結果です。

問題は、**多くのデータ提供は「最新の値」しか返さない**ことです。過去の時点の数値を引くと、その時点の値ではなく「今から見た、その時点の値」が返ってきます。

これが困るのは、たとえばこういう場面です。

> 2026年5月に「成長率1.2%」という前提で立てた計画があった。あとから振り返ると数字は0.8%に改定されている。**当時の判断は、間違った数字に基づいていたのか、それとも当時得られる情報の範囲では妥当だったのか。**

これを区別するには、「いつ時点で公表されていた値か」を残しておく必要があります。

![同じ2026年4-6月期の値が、8月時点では1.2%、11月時点では改定されて0.8%になる図。改定後も8/15公表の版が残っており、2つの版が並んで記録されている](./economic-data-square-bitemporal.webp)

そこで、このサイトでは**すべての観測値に2つの時間軸を持たせています**。ひとつは「いつのデータか」（2026年4-6月期）、もうひとつは「いつ公表された版か」（2026年8月15日発表）。データベースの世界でバイテンポラルと呼ばれる持ち方です。

改定があっても古い版を上書きせず、新しい版を追加します。結果として、**当時公表されていた値をあとから再現できます**。

正直に言うと、この機能は現在まだ画面には出していません。蓄積は公開初日から始めていますが、UIとしてどう見せるべきかを決めきれていないためです。ただ、**蓄積は「あとから始める」ことができません**。今日から貯めなければ、来年になっても去年の版は手に入らない。だから機能として出す前に、蓄積だけ先に始めています。

## 13機関を1本のパイプラインに揃える

データソースを増やすときに毎回ぶつかるのが、機関ごとの癖です。実例をいくつか挙げます。

**そもそもAPIがない。** 厚生労働省の有効求人倍率や経済産業省の第3次産業活動指数は、e-Statの統計APIに載っていません。ただしe-Statのファイルダウンロードには Excel が置かれている。この「APIはないがファイルはある」という状態のものが、実務で必要な統計に少なからずあります。

**期間軸が「時間」とは限らない。** 人口推計や毎月勤労統計のように、表の軸が時点ではなく別の分類になっている表があります。素直に「1列目が時間」と決め打つと壊れます。

**同じ表から複数の切り口を取りたい。** 消費者物価指数は1つの統計表ですが、総合・品目別・地域別という3つの見方があります。これを別々の系列として扱えないと、使い物になりません。

こういう差異は、取り込みの層で吸収して、**そこから先には同じ形で流す**という方針にしています。ソースが増えても、グラフを描く側のコードは変わらない。

もうひとつ決めたのは、**辻褄が合わないときは黙って通さない**ことです。たとえば第3次産業活動指数には「総合＝各業種×ウェイトの加重平均」という恒等式があります。取り込み時にこれを検算して、合わなければ処理を止めます。

最初は「指数系の統計は突合を諦める」つもりでした。ところが配布ファイル自体にウェイト列が入っていることに後から気づき、検算できるようになった。**諦める前に、配布されているものを最後まで見るべきでした。**

## 統計の名前を機械翻訳しない

英語版も用意していますが、ひとつ決めていることがあります。**統計の名前は、公表元が英語名を出しているものだけを英語で表示する**というルールです。

世界銀行のデータは元から英語名があるので、そのまま出します。一方、日本の統計で公式な英語名が確認できていないものは、日本語名のまま出しています。

英語のページに日本語が混ざるのは、見た目としては中途半端です。それでも機械翻訳した統計名を配らないことにしたのは、**統計の名前は識別子だから**です。「毎月勤労統計調査」を機械翻訳した名前で引用されて、それが別の統計を指しているように見えたら、翻訳した側の責任になります。見た目の統一より、名前が指すものが正しいことを優先しました。

## 作り方

このサイトは、コードのほとんどを Claude Code に書かせています。バックエンドは Python（FastAPI）、フロントは Next.js、データベースは PostgreSQL です。

うまくいったのは、**設計上の判断とその理由をドキュメントに書き残す運用**でした。「なぜこうなっているか」「何を試して棄却したか」を残しておくと、次のセッションで同じ議論を繰り返さずに済みます。逆に言うと、これを怠ると同じ判断を何度もやり直すことになります。

もうひとつ効いたのは、**壊れたら止まるテストを先に置く**ことです。たとえば「英語画面に日本語が直書きされていないか」をソースコードを走査して検出するテストがあります。画面を目で見て確認する方式では、エラー表示や、押すまで開かないポップアップの中身までは追えません。実際、目視で「日本語ゼロ」と判断した裏で、グラフ1枚が丸ごと日本語のまま残っていたことがありました。

## 現在地とこれから

β版として公開中です。機能の追加や画面の変更が続きますし、表示や数値に誤りが残っている可能性もあります。気づかれた点があれば教えていただけると助かります。

REST API と MCP（AIエージェントから直接データを引く仕組み）については、有料プランでの提供を予定しています。開始時期は未定です。
