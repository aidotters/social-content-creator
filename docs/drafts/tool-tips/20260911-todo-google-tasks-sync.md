リポジトリの TODO は Markdown で持ちたい、と思っていました。git の履歴に残りますし、エディタでそのまま開けます。

ただ、外出先で困ります。

スマホでリポジトリを開いて `TODO.md` を読むというのは、できなくはないのですが、やりません。結局スマホからは見なくなります。

Google Workspace を使っているので、Google ToDo（Google Tasks）と同期できれば済むはずでした。

そこで「常時走る双方向同期」を作るつもりで調べ始めて、設計を2回ひっくり返すことになりました。最終的に、常駐の自動同期は作っていません。

先に結論を書きます。双方向同期で効くのは「双方向かどうか」ではありませんでした。**どちらを正とするかを先に決めること**と、**ID の対応表を永続化すること**。この2つでほとんど決まります。そして**競合を自動で解決しない**ほうが、結局こわれません。

今回は、そこに至るまでに決めたことと、あえて決めなかったことを書いていきます。

## Google Tasks API にできないこと

まずは API 側に何があるかを調べました。カレンダーや Drive と同じ感覚でいると、いくつか足をすくわれます。

| 観点 | Google Tasks API v1 の状況 |
|---|---|
| 増分同期 | `syncToken` / `nextSyncToken` が**存在しない**。公式の代替も文書化されていない |
| プッシュ通知 | `watch` / `channels` が**存在しない** |
| 差分検知 | `updatedMin` はある。`deleted` フラグと `showDeleted=true` で削除済みも取れる |
| 楽観ロック | `etag` はあるが、`If-Match` や 412 の挙動が公式文書に記載がない |
| 期日 | **日付のみ。時刻は破棄され、API から読み書きできない** |
| 繰り返し | 相当するフィールドが**存在しない** |
| サブタスク | **1階層のみ** |
| 文字数 | タイトル 1,024 字 / メモ 8,192 字、プレーンテキスト |
| クォータ | 1日 50,000 クエリ |
| スコープ | **「tasks」と「tasks.readonly」の2つだけ** |

設計を変えたのは、このうち2つです。

ひとつは、増分同期もプッシュ通知も無いこと。変更を教えてもらう手段が無いので、**ポーリングしか選べません**。

もうひとつはスコープです。Drive の「drive.file」にあたる「アプリが作ったものだけ」という限定が、Tasks には用意されていません。「tasks」を要求すると、**ユーザーの全タスクリストに手が届きます**。これは、あとで実装しないものを決める理由になりました。

なお、完了・非表示・削除済みを取得するフラグは、既定値が公式ページの間で食い違っています。読んで悩むより、常に明示して呼ぶことにしました。

ここに挙げた内容は、[REST リファレンス](https://developers.google.com/workspace/tasks/reference/rest)と[利用上限のページ](https://developers.google.com/workspace/tasks/limits)で確かめたものです。

## 決めたこと1: 常駐させない

ポーリング確定なら、次はどのくらいの頻度で回すか、という話になります。そこで一度立ち止まりました。

対象は1人分のタスクリスト1本です。全件を取っても、`tasklists.list` が1回と、100件あたり `tasks.list` が1回で済みます。

この規模で常駐プロセスを抱える理由が、どうも見当たりません。

そこで、**人が起動する reconcile** にしました。走らせたいときに走らせて、突き合わせて、終わる。それだけです。

なお、`updatedMin` による増分取得も使っていません。「削除されたときに `updated` が動くか」が公式に明記されておらず、そこに依存したくなかったからです。全件を取れば、この疑問そのものが消えます。

## 決めたこと2: 消えているかどうかの権威を Google 側に置く

双方向同期でいちばん危ないのは、削除です。

片側で消えたものを、もう片側からも消す。素直に書くとそうなります。ただ、**この設計は事故が非可逆になります**。

そこで、存在の権威を Google 側に固定しました。スマホで消したら消えます。

一方で `TODO.md` から行を消しても Google には残るので、**次の同期でその行は戻ってきます**。

一見おせっかいですし、慣れるまでは「消したのに戻ってきた」と思います。それでもこちらを選んだのは、消す操作の入口を1つに絞ったほうが、運用の説明が短くなるからです。

「消すときはスマホか Web で消す」。これ以上短く書けません。

## 決めたこと3: ID の対応表と三方比較

次は、どの行がどのタスクなのか、という対応づけです。

まずは、タイトルの一致で突き合わせる方法を考えました。対応表を持たなくて済むので手軽に見えます。

ただ、これは**タイトルを書き換えただけで「削除＋新規作成」に見えます**。同じタスクの名前を直しただけなのに、消して作り直す扱いになってしまう。

そこで、ID を行に埋めることにしました。書式はこうです。

```markdown
- [ ] 請求書を送る @2026-09-15 <!--gt:MTIzNDU-->
  > 先方の担当は経理部
  - [x] 金額を確認する <!--gt:Njc4OTA-->

## 完了

- [x] ロゴを差し替える <!--gt:QUJDREU-->
```

行末の `<!--gt:...-->` が Google のタスク ID です。ID の無い行は新規として作られ、ID が書き戻されます。

そのうえで、前回同期した時点の値を対応表として別ファイルに残しています。

手元・Google・前回値の3つが揃うと、どちらが動いたのかをフィールド単位で判定できます。

| 手元が前回と同じ | Google が前回と同じ | 判定 |
|---|---|---|
| ○ | ○ | 変更なし |
| ○ | ✗ | Google を採用（`TODO.md` を書き換える） |
| ✗ | ○ | 手元を採用（Google を patch する） |
| ✗ | ✗ | 競合。どちらも書き換えず、人に報告する |

最後の行が要点で、**競合を自動で解決しません**。

どちらかを機械的に勝たせると、負けた側の編集が黙って消えます。黙って消えるより、止まって報告されるほうがましだと判断しました。

なお、期日は変わったときだけ送っています。Tasks API は期日を設定すると時刻を落とすので、変更が無いのに送り直すと、スマホで付けた「15時」が消えてしまうためです。

完了タスクの整理にも、小さな判断がありました。完了から30日を過ぎた行は `TODO.md` から取り除きます（Google 側には残します）。

ここで効くのは、**この窓を実行時刻に連動させない**ことです。「直近1週間」のように実行のたびにずれる窓にすると、古い状態を突き合わせたときに重複が生まれます。

## こわれないための門番

このスクリプトが最終的に触るのは `TODO.md` と Google Tasks で、どちらも壊れると困ります。そこで、おかしいと思ったら**書き込む前に止まる**ようにしました。

取得が0件なのに対応表に項目がある場合は、異常終了します。取り違えや API の不調を「全部消された」と読まないためです。

対応表に記録したリスト ID と、いま掴んでいるリストが違う場合も止まります。ここを通すと `TODO.md` が丸ごと消えかねません。

同じタスク ID が2行にある場合も止まります。同じタスクへの更新が2件出て、行の順番で編集が消えるからです。

ただ、リストの作成と削除については、そもそも実装していません。スコープが全リストに届いてしまう以上、コード側で専用リスト1本に閉じるしかなく、**リストを削除するコードを書かないことが最後の歯止め**になります。

結果は終了コードで区別できるようにしました。「0」が正常、「1」が書き込む前に停止、「2」が競合あり（競合していない分は適用済み）、「3」が一部の書き込みに失敗、です。3のときは次の同期で再試行されます。

## 別モデルのレビューに意味はあったか

実装のあと、2回レビューしました。1回目は同一ホストの検証エージェント（Claude Code）、2回目は別モデル（Codex）です【注】。

> **【注】レビューの設定と運用**
>
> 実装担当と別のモデルにレビューさせる、という運用ルールを置いています。
>
> 1回目は Claude Code の検証サブエージェント（`spec-driven-dev:implementation-validator`）を、実装したのと同じホストで走らせました。ただし**これは実装担当と別モデルである保証がありません**。そこは記録にも「確認できていない」と残してあります。
>
> そこで2回目を Codex に投げました。Claude Code の Codex プラグイン経由で、未コミットの変更なら `/codex:review --wait`、コミット済みのブランチ差分なら `/codex:review --base main --wait` です。
>
> 依頼は2点に絞ります。**「1回目と同じ指摘ではなく、見落としを探すこと」「修正はせず、指摘だけ返すこと」。** 修正は実装担当が引き取ります。そして**レビュー中は対象のコードを変更しません**。差分が動くと、指摘がどの状態に対するものか分からなくなるためです。
>
> 指摘と対応は `.steering/<作業フォルダ>/cross-review.md` に表で残します。どの指摘をどう直したか、どれをあえて直さなかったかを、あとから引けるようにするためです。

結論から書くと、意味はありました。

1回目が9件、2回目が11件です。効いたのは、**2回目が見ているのが1回目の指摘を全部直したあとのコードだ**という点でした。それでも高重大度が6件出ています。

見る場所も違いました。1回目は状態の持ち方に、2回目は入力の形（CRLF、日付で終わるタイトル、ID の重複）に寄っています。

さらに、1回目の高重大度3件が**どれもテストの無い適用フェーズに集まっていました**。そこも純関数へ切り出してテストを足しています（現在83件）。レビューが設計に跳ね返った形です。

まとめると、**別モデルによるレビューはあったほうが良い**、ということになりそうです。

## 残っている制約

冒頭に書いた2つが決まると、あとの実装で迷うことはほとんどありませんでした。ただ、できないことも残っています。

既存タスクの親子の付け替えは同期の対象外で、Google Tasks 側で動かします。繰り返しタスク・優先度・タグ・添付は Google Tasks 側に無いので扱えません。時刻つきのリマインドはカレンダーの仕事だと割り切りました。

なお、Google Tasks は worktree で分離されない共有資源なので、**同期を走らせるのは常に1セッションだけ**にしています。

「常駐する双方向同期」を作ろうとしていたころに比べると、できることはずいぶん減りました。ただ、外出先でスマホから TODO を見るという当初の目的は、これで満たせています。
